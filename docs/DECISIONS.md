## Architecture decision records

| ID | Date | Decision | Why | Alternatives considered |
|----|------|----------|-----|-------------------------|
| ADR-001 | 2026-10-27 | Target **.NET 10 (LTS)**, pinned with `global.json` (`version 10.0.100`, `rollForward latestFeature`). | The machine also has the .NET 11 RC SDK, which would otherwise be picked as the newest; a portfolio project should build on the released LTS with the same SDK on every machine and in CI. `latestFeature` accepts any 10.0.x SDK, never 11. | .NET 11 RC (pre-release tooling, breaks CI parity); no pin (SDK choice depends on the machine). |
| ADR-002 | 2026-10-27 | **LF line endings** in the repository, enforced by `.gitattributes` (`* text=auto eol=lf`); `.bat/.cmd/.ps1` keep CRLF. `.editorconfig` sets `end_of_line = lf`. | Linux containers, CI runners and Docker builds see consistent files; no CRLF/LF noise in diffs between Windows and Linux. Visual Studio handles LF natively. | CRLF (Windows default; noisy diffs in Docker/CI, `#!` scripts break). |
| ADR-003 | 2026-10-28 | Solution file format **`.slnx`** (`Mercato.slnx`). | Default in Visual Studio 2026 and the .NET 10 SDK; plain XML, one line per project, readable diffs and no GUID merge conflicts. Supported by `dotnet`, VS 2022 17.13+, Rider, GitHub Actions, Azure Pipelines. Reversible with `dotnet sln migrate`. | Legacy `.sln` (GUID-heavy text format, kept only for compatibility). |
| ADR-004 | 2026-10-28 | **Central Package Management**: all NuGet versions in `Directory.Packages.props`; project files reference packages without `Version`. | One place to bump versions; two projects can never disagree on a package version; required for the multi-project/multi-service layout. | Versions per `.csproj` (drifts as the project count grows). |
| ADR-005 | 2026-10-28 | **Shared build settings** in `Directory.Build.props`: `net10.0`, `Nullable`, `ImplicitUsings`, `Deterministic`, `AnalysisLevel latest-recommended`, `EnforceCodeStyleInBuild`, `TreatWarningsAsErrors`, `GenerateDocumentationFile` (+ `NoWarn CS1591`). Style rules in `.editorconfig`. Deviation: `IDE0058` (expression value never used) off because ASP.NET/host builder APIs are fluent. | GeneralRules §6/§13 ask for analyzers at `latest-recommended` with warnings as errors; one file means every current and future project (services, tests, tools) inherits them. `GenerateDocumentationFile` is needed for IDE0005 (unused usings) to run in the build; CS1591 is suppressed so XML docs are not mandatory on every public member. | Settings per project (drift); analyzers as warnings only (ignored over time). |
| ADR-006 | 2026-10-27 | **Two requirements documents**: `REQUIREMENTS.md` is the final goal; `REQUIREMENTS-V1.md` is the build target — every module, minimal use cases, three roles. Same requirement IDs in both; items migrate one at a time via the growth path in V1 §8. `ARCHITECTURE.md` is shared by both (V1 reduces footprint, not structure). | Learning project: the architecture and technologies are the point, not functional completeness. A thin end-to-end path through every module gets to the technology work (events, saga, gateway, Docker, K8s) fastest. | One full requirements doc (too much to build before reaching the interesting technology); a V1-specific architecture (would have to be rebuilt when growing). |
| ADR-007 | 2026-10-29 | **Angular 22** skeleton in `web/mercato-web` via `ng new`: standalone components, signals, SCSS, no SSR, Vitest, Prettier, npm, `--skip-git` (one repository). Angular's generated best-practices guidance adopted as `docs/Rules/AngularRules.md`; the generated `CLAUDE.md`/`AGENTS.md`/`.mcp.json` are deleted. | Current Angular major, matches PLAN.md §5 (standalone, signals). Rules belong in `docs/Rules/`, one `CLAUDE.md` per repo, no MCP server registered by a generator (GR-10). | SSR (not needed for an app behind an API); CSS instead of SCSS (Material prefers SCSS); keeping the nested AI files (duplicate instructions, silent MCP registration). |
| ADR-008 | 2026-11-08 | `Money` and `ShippingAddress` are **records**; no `ValueObject` base class. | A record gives value equality, immutability and `with` for free; a base class would only repeat that. Less code to learn and to test. | Abstract `ValueObject` base with `GetEqualityComponents()` (boilerplate for two types). |
| ADR-009 | 2026-11-08 | Shared **`Guard`** helper in `Mercato.Domain/Common` for argument checks. | The same null/empty/length checks appeared in several aggregates; extracted on repetition (K-08) so the rules read the same everywhere. | Checks inline in each class (copies drift); a validation library in the Domain (dependency for little gain). |
| ADR-010 | 2026-11-08 | Domain events live in **one `Events` folder per module** (namespace `...<Module>.Events`). | Events are the module's published language; one folder makes them easy to find and later to move into `Mercato.Contracts`. | Event next to the aggregate that raises it (scattered); one global events folder (breaks module boundaries). |
| ADR-011 | 2026-11-08 | `StockHold` is a child of `InventoryItem`; **one hold per cart and product**, replaced when the quantity changes. | Availability is `OnHand − Reserved − active holds`; keeping holds inside the aggregate lets `InventoryItem` enforce that rule in one transaction with a rowversion (TR-43). | Separate `StockHold` aggregate (cross-aggregate consistency problem); hold stored only in the cart. |
| ADR-012 | 2026-11-08 | `CartItem` stores **`HoldExpiresAt`** instead of a `HoldId`; a checked-out cart keeps its items (`CartStatus.CheckedOut`). | The cart only needs to know when its reservation ends; no id coupling to the Inventory module (TR-12). Keeping items on a checked-out cart preserves what was bought. | `HoldId` reference to a hold (cross-module id coupling); deleting the cart items at checkout (loses history). |
| ADR-013 | 2026-11-08 | **Per-module transition exceptions** (`InvalidOrderTransitionException`, `InvalidPaymentTransitionException`, ...) instead of one shared class. | Each module owns its own failure vocabulary; no shared type that couples modules. | One `InvalidTransitionException` in `Common` (every module depends on it). |
| ADR-014 | 2026-11-08 | **`User` is deferred to Phase 4.** Until then `CustomerId` / `UserId` are plain `Guid`s. | ASP.NET Core Identity owns users and roles; modelling `User` now would be thrown away. | A placeholder `User` aggregate now. |
| ADR-015 | 2026-11-08 | A **`Product` is one vendor's listing** (carries `VendorId`); no shared product with several vendor offers in V1. | Keeps tenancy (TR-15), stock and pricing simple: one product, one vendor, one stock row. SKU is unique per vendor. | Shared catalogue product with per-vendor offers (like a marketplace listing page); revisit after V1. |
| ADR-016 | 2026-11-08 | EF Core mapping lives in **`IEntityTypeConfiguration<T>` classes** in Infrastructure, loaded with `ApplyConfigurationsFromAssembly`. | The Domain stays free of persistence attributes and of any EF reference; one configuration file per aggregate part. | Data annotations on domain classes (couples Domain to EF); everything inside `OnModelCreating` (one huge method). |
| ADR-017 | 2026-11-08 | **Foreign keys only inside a module** (Catalog: `Product` to `Vendor`/`Category`, `Restrict`); across modules only ids (TR-12). | Modules must stay extractable (Phases 8-9); a cross-module FK would block moving a table to another database. `Restrict` stops deleting a vendor or category that still has products. | FKs everywhere (simpler SQL, but couples modules); cascade delete on the catalog (silent data loss). |
| ADR-018 | 2026-11-08 | `Money` is stored as **`...Amount decimal(18,2)` + `...Currency nchar(3)`** via `OwnsOne`, through one shared **`OwnsMoney`** helper. | TR-44. Owned type keeps `Money` a value object with no extra table; the helper was extracted on the third use (K-08). A prefix is mandatory, hence `PaymentAmount`/`PaymentCurrency`. | A `Money` table (a join for every price); value converter to one string column (not queryable). |
| ADR-019 | 2026-11-08 | **`DateTimeOffset`** in the domain, stored as **`datetimeoffset`** instead of `datetime2` (deviation from TR-44). | Keeps the UTC offset in the database and matches the C# type one to one; no conversion code. | `datetime2` with UTC by convention (offset lost, convention must be remembered). |
| ADR-020 | 2026-11-08 | **Enums are stored as strings** (`HasConversion<string>()`); child entities use shadow foreign keys with cascade delete. | Readable in SSMS and safe against reordering the enum; children (`CartItem`, `StockHold`, `VendorOrder`, `OrderItem`) do not need a CLR foreign-key property and die with their root. | Integer enums (opaque rows, reorder risk); explicit FK properties on children (noise in the domain). |
| ADR-021 | 2026-11-08 | V1 uniqueness: **one `Payment` per order, one `Shipment` per vendor order.** | Matches the V1 flows; enforced by unique indexes. Revisit for payment retries or partial shipments. | Non-unique indexes with the rule only in code. |
| ADR-022 | 2026-11-08 | **DTOs and repositories are Phase 3** (Application layer): ports such as `IProductRepository` in Application, adapters in `Infrastructure/Persistence/Repositories/<Module>/`; reads bypass repositories through EF projections (TR-20). | No use cases exist yet, so any repository now would be guesswork; see `LearningProcess.md` section 7. | Generic repository now (leaks `IQueryable`, adds nothing over `DbContext`). |
| ADR-023 | 2026-11-08 | **SQL Server 2022 (Developer image) in Docker** via `deploy/compose/infra.yml`; the SA password is read from the git-ignored `deploy/compose/.env` (`.env.example` holds a placeholder); data kept in the named volume `sqlserver-data`; the connection string is a user-secret (`ConnectionStrings:Mercato`). | Same engine family as the planned Azure SQL, no local install, one command to rebuild; no secret in Git (GR-32). | Local SQL Server install or LocalDB (not reproducible, not containerised); SQLite (different SQL dialect, no rowversion); password in `appsettings` (secret in Git). |
| ADR-024 | 2026-11-08 | **Migrations** live in `Mercato.Infrastructure/Persistence/Migrations`; the `dotnet-ef` **local tool** is pinned in `dotnet-tools.json`; migrations are **applied at startup in Development only** (TR-42). | Everyone gets the same tool version; a fresh clone builds its database on first run. Production gets migrations from the deployment pipeline, never from the app. | Global `dotnet-ef` (version drift); auto-migrate in every environment (unsafe for production). |
| ADR-025 | 2026-11-08 | **Seed data** is inserted by `DevelopmentDataSeeder` (Development only) through the domain factories, idempotent, in one `SaveChanges`; not by EF `HasData`. | `HasData` would freeze fixed Guids and raw values into migrations and bypass the domain rules; the seeder reuses the same validation as real code. | `HasData` in the configurations; SQL seed scripts (bypass the domain). |

## Phase log

### Phase 1 – Setup & solution structure
- **Status:** Done 2026-10-29. Unit-test projects deferred to Phase 11 (Testing) at the user's request.
- **Built:**
  - Root: `global.json` (.NET 10 pin), `.gitignore`, `.gitattributes` (LF), `.editorconfig` (GeneralRules §6 as enforceable rules; IDE0058 off), `Directory.Build.props` (shared settings, analyzers `latest-recommended`, warnings as errors, `EnforceCodeStyleInBuild`, `GenerateDocumentationFile` + `NoWarn CS1591`), `Directory.Packages.props` (CPM), `Mercato.slnx`, `README.md`, `CLAUDE.md`.
  - `src/`: `Mercato.Domain`, `Mercato.Contracts` (no references), `Mercato.Application` (→ Domain, Contracts), `Mercato.Infrastructure` (→ Application), `Mercato.Api` (ASP.NET Core Web API, minimal APIs, OpenAPI; → Application, Infrastructure), `Mercato.Worker` (Worker Service; → Application, Infrastructure). Class libraries are empty shells. Template code rewritten to the rules (explicit types, weather sample removed, sealed `Worker` with constructor injection, `ConfigureAwait(false)`, PascalCase log placeholders, 10 s heartbeat). Whole solution builds with 0 warnings, `dotnet format --verify-no-changes` clean.
  - `web/mercato-web`: Angular 22.2 skeleton (`ng new`, standalone, signals, SCSS, no SSR, Vitest, Prettier); `npm run build` clean. Not part of the `.slnx`.
  - `docs/`: `REQUIREMENTS.md` (final goal), `REQUIREMENTS-V1.md` (build target, growth path), `ARCHITECTURE.md` (deployables, dependency rule TR-01…08, modules TR-10…15, request/event flows, data ownership, cross-cutting, environments, evolution path, V1 footprint), `LearningProcess.md` (why layers/modules, use case → code method), `Rules/AngularRules.md`.
  - Git: public repo `github.com/paultarce18/Mercato`, `main`, per-repo identity `paultarce18` + personal e-mail. Commits `bb3f752`, `88bd9e8`, plus the Phase 1 closing commit.
- **Decisions:** ADR-001…007. Working agreement: user creates projects/references by hand in Visual Studio with the concept explained first; Claude writes config/bulk files only on request and reads every write back from disk (GR-01); Claude can build a staged copy of the solution with its own .NET 10 SDK to reproduce errors. Minimal APIs for the Api template; controllers vs. minimal APIs decided for real in Phase 3.
- **Known issues / TODO:**
  - Commit `88bd9e8` message not in Conventional Commits form (GR-22); apply the format from now on.
  - `docs/ToDoTemp.md` is tracked and empty — keep or ignore deliberately.
  - The file-sync tool once reported a write as successful that did not land (2026-10-27); caught by the GR-01 read-back. Keep reading back.
  - `Mercato.Api` has no `UserSecretsId` yet — add in Phase 2 when the connection string is first needed.
  - Angular: `angular.json` budgets and `environments/` files are template defaults; adjust in Phase 5.
- **Next:** Phase 2 — Domain model & database: aggregates for the V1 footprint (ARCHITECTURE.md §15), EF Core + SQL Server in Docker, first migration, seed data, SSMS connected. New chat per PLAN.md §2. First GR-10 approvals there: EF Core packages, SQL Server Docker image.

### Phase 2 – Domain model & database
- **Status:** Done 2026-11-08. SSMS check passed: 6 schemas, 13 tables, 17 indexes; all foreign keys inside a module; seed data present; a second start does not duplicate it.
- **Built:**
  - Domain (`Mercato.Domain`): aggregates `Vendor`, `Category`, `Product`, `InventoryItem` (+ `StockHold`), `Cart` (+ `CartItem`), `Order` (+ `VendorOrder`, `OrderItem`), `Payment`, `Shipment`, `Notification`; `Money` and `ShippingAddress` records; `Guard`, `DomainEvent`, per-module events and exceptions; Ordering split into `Enums` / `Events` / `Exceptions` subfolders.
  - Persistence (`Mercato.Infrastructure/Persistence`): `MercatoDbContext` (nine `DbSet`s), 13 `IEntityTypeConfiguration` classes, shared `OwnsMoney` helper, one schema per module, filtered unique index for one active cart per customer, rowversion on `InventoryItem`, `Migrations/` (`InitialCreate`, designer, snapshot), `Seeding/DevelopmentDataSeeder`.
  - Wiring: `AddInfrastructure(IConfiguration)` registers the DbContext with SQL Server; `Program.cs` applies migrations and seeds in Development only; `UserSecretsId` on `Mercato.Api`; `dotnet-tools.json` pins `dotnet-ef` 10.0.14.
  - Infrastructure: `deploy/compose/infra.yml` (SQL Server 2022 container `mercato-sqlserver`, volume `sqlserver-data`), `deploy/compose/.env.example`.
  - Docs: `docs/DBArchitecture.md` (tables, relations, rules), `LearningProcess.md` section 7 (DTOs, repositories), this log.
- **Decisions:** ADR-008…025 (see table). Working mode: the user types the EF Core code in Visual Studio, Claude explains and reviews; Claude can build a copy of the user's files with its own SDK to reproduce errors.
- **Known issues / TODO:**
  - `ProductConfiguration` still has the old `OwnsOne(...)` block as comments (kept on purpose) and a redundant `Navigation(...).IsRequired()` line.
  - `dotnet ef` reports only "Build failed" when analyzers fail the build (an IDE0130 namespace error did): run `dotnet build` first to see the real message.
  - Docker Desktop on Windows needs the Virtual Machine Platform / WSL feature; the installer fails without it.
  - Stray log `FirstMercatoRun.txt` in the repo root must not be committed.
  - Payment retries, partial shipments and a shared multi-vendor product are not supported in V1 (ADR-015, ADR-021).
- **Next:** Phase 3 — API core: CQRS handlers, validation, repositories and DTOs (ADR-022), versioning, OpenAPI UI, middleware, ProblemDetails, logging. First GR-10 approvals there: MediatR-style library choice (or hand-rolled), FluentValidation, Serilog.
